# План: видеотрансляция с камеры в «кружочках» онлайн

**Цель:** в онлайне показывать живое видео и звук с камеры/микрофона в кружочках рядом с игроками в лобби — голосовое и визуальное общение.

---

## Видео + звук: сложность, нагрузка на сервер, что нужно

### Сложно ли?

**Умеренно.** Не тривиально, но без «ракетной науки»:

- **Код:** на клиенте — запрос камеры и микрофона (`getUserMedia({ video: true, audio: true })`), WebRTC (создание `RTCPeerConnection`, добавление треков, приём удалённых потоков). На сервере — только **сигналинг**: передача коротких сообщений (offer/answer/ICE), без передачи самого видео и звука.
- **Объём:** ориентировочно 200–400 строк клиентского JS (менеджер peer-соединений, привязка к списку игроков в лобби) + несколько событий Socket.IO на сервере (десятки строк).
- **Подводные камни:** права доступа к микрофону, разное поведение iOS/Android, возможные проблемы с NAT (решаются STUN/TURN).

### Нагрузка на сервер

При схеме **WebRTC P2P** (рекомендуется для лобби 2–6 человек):

| Что гоняет сервер | Нагрузка |
|-------------------|----------|
| Видео и звук      | **Нет.** Трафик идёт напрямую между браузерами (peer-to-peer). |
| Сигналинг (SDP, ICE) | Только маленькие JSON-сообщения при установке/обновлении соединений. Несколько килобайт на комнату при входе/реконнекте. |

**Итог:** сервер почти не нагружается медиа-трафиком. Рост нагрузки — только от числа комнат и реконнектов (больше сигнальных сообщений), а не от длительности звонка.

Если позже использовать **медиа-сервер (SFU)**: тогда сервер уже пересылает видео/аудио — нужен отдельный процесс (mediasoup, Livekit и т.п.), больше CPU и канал; для первого этапа не обязательно.

### Что дополнительно нужно

1. **На клиенте (браузер):**
   - Запрос **камеры и микрофона** (`getUserMedia` с `audio: true`).
   - В один и тот же `MediaStream` добавить и видео-, и аудиотрек и передавать его в WebRTC (один поток на участника — и картинка, и голос).

2. **На сервере (ваш Node.js):**
   - Только **сигналинг**: новые события, например `webrtc_offer`, `webrtc_answer`, `webrtc_ice`. Сервер принимает сообщение от одного сокета и пересылает нужному участнику комнаты (по `targetPlayerId` или по socket id). Никаких медиа-библиотек на сервере не нужно.

3. **STUN (желательно с первого дня):**
   - Чтобы соединения поднимались из-за NAT, нужен STUN-сервер. Можно бесплатный публичный (например, `stun:stun.l.google.com:19302`) — прописать в конфиге ICE при создании `RTCPeerConnection`. Сервер свой для STUN поднимать не обязательно.

4. **TURN (опционально, «на потом»):**
   - Если у части пользователей не удаётся установить P2P (жёсткий firewall, симметричный NAT), понадобится TURN-сервер — он ретранслирует медиа. Можно добавить позже (например, coturn на VPS или платный сервис).

5. **HTTPS (или localhost):**
   - `getUserMedia` в современных браузерах работает только на безопасном контексте (HTTPS или localhost). Для продакшена — нормальный SSL.

6. **Интерфейс:**
   - Кружки в лобби с `<video>` для каждого участника; для удалённых потоков звук можно по умолчанию включить (без muted), чтобы голос шёл сразу, или добавить кнопку «вкл/выкл звук» по желанию.

**Итого по «что нужно»:** доработка клиента (getUserMedia + WebRTC + привязка к UI), несколько событий сигналинга на текущем сервере, STUN-URL в конфиге; отдельный медиа-сервер и TURN — по необходимости позже.

## 1. Можно ли это сделать технически

**Да.** Браузеры (в т.ч. на телефонах) умеют:

- Захватывать камеру и микрофон: **`navigator.mediaDevices.getUserMedia({ video: true, audio: true })`**
- Показывать свой поток в `<video>`, передавать видео и звук другим участникам через **WebRTC** (в один поток добавляются и видео-, и аудиотреки).

Ограничения:

- Нужно разрешение пользователя на камеру.
- На мобильных — расход батареи и трафика, возможны задержки.
- В игре уже есть ориентация «только альбом» — камера на телефоне будет снимать в этой ориентации (обычно нормально).

---

## 2. Где показывать «кружочки» с видео

Сейчас в лобби список игроков — просто имена в `#lobby-players` (без кружков). Варианты:

| Вариант | Описание |
|--------|----------|
| **A** | Заменить или дополнить каждый пункт списка в лобби: слева круг с видео (или аватар/заглушка), справа имя. |
| **B** | Отдельный блок «Участники» с кружками (аватар/видео) + имена, общий для лобби и, при желании, для экрана игры. |
| **C** | Маленькие кружки в углу экрана (как в Zoom): только видео, по клику — увеличение или звук. |

Рекомендация: начать с **A** или **B** в лобби — круг слева от имени, внутри либо превью камеры, либо заглушка «нет камеры».

## 3. Как передавать видео между участниками

### Вариант 1: WebRTC «каждый с каждым» (P2P)

- Между каждой парой участников поднимается отдельный peer-connection, видеопоток идёт напрямую.
- **Плюсы:** сервер не гоняет видео, меньше задержка, не нужен медиа-сервер.
- **Минусы:** при N игроках у каждого (N−1) исходящих потоков; на телефоне при 4–6 участниках возможна нагрузка и расход трафика.
- Нужен **сигнальный канал** (обмен SDP/ICE) — его уже можно делать через текущий Socket.IO и комнаты.

### Вариант 2: WebRTC через медиа-сервер (SFU)

- Каждый шлёт один поток на сервер (например, **mediasoup**, **Janus**, **Livekit**). Сервер раздаёт потоки остальным.
- **Плюсы:** у клиента один исходящий поток, лучше масштабируется и ведёт себя на мобильных.
- **Минусы:** нужен отдельный сервис/процесс, настройка TURN/STUN, сложнее развёртывание.

### Вариант 3: Релей через Node (не WebRTC)

- Клиент пушит кадры (например, через WebSocket) на сервер, сервер рассылает их в комнату.
- **Плюсы:** проще логика, один тип транспорта.
- **Минусы:** огромная нагрузка на сервер и трафик, большая задержка, обычно нереалистично для видео в реальном времени.

**Рекомендация:** для 2–6 человек в комнате разумно начать с **Варианта 1 (P2P)**. Если появятся проблемы с производительностью на мобильных — рассматривать **Вариант 2 (SFU)**.

## 4. Пошаговый план внедрения (P2P)

1. **Разрешение и локальный превью**
   - В лобби (или по кнопке «Включить камеру») запрашивать `getUserMedia`, показывать свой поток в своём кружке.
   - Состояние: «камера вкл/выкл», при отказе — показывать заглушку.

2. **Сигналинг через Socket.IO**
   - События в духе: `webrtc_offer`, `webrtc_answer`, `webrtc_ice` с полями `targetPlayerId` / `roomCode`.
   - При входе в комнату каждый получает список участников и с уже сидящими в комнате обменивается SDP и ICE-кандидатами.

3. **WebRTC у каждого клиента**
   - Для каждого другого игрока в комнате создавать `RTCPeerConnection`, привязывать свой медиапоток — и видео, и аудио (addTrack по обоим трекам), обрабатывать входящие треки: видео — в `<video>`, аудио — автоматически воспроизводится (или привязать к элементу).
   - Обработка отключения (игрок вышел) — закрытие соответствующей peer-connection и скрытие/заглушка в кружке.

4. **UI**
   - В каждом пункте списка игроков (или в блоке «Участники»): круг (например, 48–64px) + имя.
   - В круге: `<video autoplay playsinline muted>` для чужих потоков; для себя — тот же поток или зеркальное превью.
   - Звук: по умолчанию можно muted для удалённых, с кнопкой «включить звук» при желании голосового общения.

5. **Мобильные и ограничения**
   - Запрос камеры после входа в комнату (или по явной кнопке), чтобы не пугать на экране приветствия.
   - На iOS обязательно `playsinline` и разрешения в манифесте/странице при необходимости.
   - При уходе со страницы/выходе из комнаты — останавливать все треки и закрывать peer-connections.

---

## 5. Упрощения и альтернативы

- **Только лобби:** показывать видео только в лобби, в игре оставить только чат и голос при желании позже.
- **Только видео:** если решите отключить звук — не добавлять аудиотрек в `getUserMedia` и в peer-connection; голос тогда через отдельный звонок (Telegram/Discord) или включить позже.
- **Вместо своей реализации:** дать в интерфейсе ссылку на общий видеозвонок (Jitsi, Meet, Zoom) — минус: уход с сайта, плюс: быстро и стабильно.

## 6. Итог

| Вопрос | Ответ |
|--------|--------|
| Показывать трансляцию с камеры в кружочках онлайн — возможно? | Да. |
| Где лучше всего? | В лобби, в списке игроков: круг (видео/заглушка) + имя. |
| Как передавать? | WebRTC P2P (видео + звук в одном потоке) с сигналингом через Socket.IO; при росте числа участников — рассмотреть SFU. |
| Нагрузка на сервер? | Только сигналинг (мелкие сообщения). Медиа идут P2P, сервер их не пересылает. |
| Что дополнительно? | getUserMedia с audio, STUN в конфиге ICE, HTTPS в продакшене; TURN — по необходимости. |
| Нужны ли антиспам/фильтры для видео? | Нет, в плане не закладывались; модерация при необходимости — отдельная тема. |

Дальше шаг реализации — добавить запрос камеры и отображение своего потока в одном кружке в лобби, затем сигналинг и P2P с одним другим участником, после чего обобщить на N участников.
